## Simulation architecture

### Verified strengths

- The simulation kernel is authoritative and has no Godot dependency.
- The cube-sphere quadtree provides stable parent/child addressing and an adaptive leaf cover.
- Simulation LOD is a state transition, not object sleeping or rendering LOD.
- `FieldStore` has explicit intensive/extensive aggregation semantics.
- `IStateStore` allows structured domains to define their own refine/coarsen behavior.
- The cohort store preserves cohort count through LOD transitions.
- Fixed-step scheduling, explicit system ordering/access declarations, commands, events, and snapshots are separated from rendering.
- Snapshots persist the exact adaptive cover and state-store payloads.
- Existing tests cover conservation, deterministic continuation within the tested build, adaptive-cover restore, command routing, and module extension.

This is a sound foundation for a world simulator. It is not yet evidence of production-scale throughput.

### Fixed in this pass: LOD transition thrashing

The previous focus policy used the same angular thresholds for entering and leaving a detail level. A camera or interest point moving around a threshold could therefore repeatedly refine and coarsen authoritative stores.

The policy now refines at the nominal thresholds and requires an additional 4-degree margin before coarsening. A regression test verifies that a refined region remains refined inside the hysteresis band and coarsens after leaving it.

This mirrors the reason Godot itself exposes hysteresis margins for render visibility ranges, while keeping simulation LOD independent from render LOD.

### Important remaining limitation: adaptive neighbors

`CubeSphereTopology::neighbors4()` returns same-level topological neighbors. An adaptive active cover can contain coarser or finer cells across a face, so this function is **not** an active-cover neighbor query.

Current shipped systems are cell-local and therefore do not currently violate this contract. Future transport, diffusion, advection, river routing, migration, trade, pathfinding, or PDE-like systems must not use `neighbors4()` as if it resolved mixed-level active neighbors.

Before such a system is implemented, add an explicit active-cover adjacency/flux contract and decide whether the cover is constrained (for example, 2:1 balanced) or whether arbitrary level differences are supported. p4est is a useful reference because it treats mixed-size neighbors and balance as first-class mesh concerns.

### Important remaining limitation: simulation fidelity is only spatial

The current policy changes cell resolution from one focus direction. All active cells still run the same system cadences and domain models.

For a persistent populated world, production simulation LOD will likely also need domain-specific fidelity: e.g. aggregate cohorts/households/economies far away, detailed local actors near active gameplay, and budget-aware update cadence. The existing `IStateStore` and scheduler boundaries can support this, but no generic importance/budget scheduler is implemented yet.

Do not add one until real domain workloads and budgets are measured.

### Static subcell detail

Refinement of intensive fields copies the parent value to children. This is correct for the generic conservation contract, but it means static geography does not automatically gain new procedural detail merely because the cover refines.

If terrain/geology requires higher-frequency information at higher simulation LOD, that must be implemented by a geography-specific hierarchical representation/refinement rule rather than changing the generic intensive-field semantics.

## Godot host audit

### Input and camera controls — fixed baseline

Previously the viewer had no user controls and rotated automatically.

The viewer now uses InputMap actions for keyboard/gamepad controls and `_unhandled_input()` for discrete gameplay/mouse input so GUI controls can consume events first. It provides orbit, zoom, camera reset, pause, and simulation speed controls.

This is a usable viewer-control baseline, not a complete accessibility/remapping menu.

### Rendering and graphics — partially fixed, not production graphics

The existing use of `MultiMesh` is appropriate for thousands of repeated cell markers. The previous script rebuilt the marker mesh, material, and MultiMesh every 250 ms. These resources are now created once and reused; only instance transforms/colors/counts are updated.

The native Godot adapter now emits render and generic field arrays from the existing dense `FieldStore` order instead of performing repeated tree/map lookups per field and cell.

A simple planet base sphere was added so the view is visually legible. Marker shadows are disabled because they add cost without useful visual information in this diagnostic visualization.

Still **not implemented**:

- terrain mesh generation / terrain render LOD;
- oceans, atmosphere, clouds, vegetation/entity presentation;
- asset streaming/chunking;
- region-split MultiMeshes for per-region frustum/occlusion culling;
- GPU-buffer/RenderingServer update path for much larger instance counts;
- profiling on target GPUs and target world workloads.

One global MultiMesh has all-or-nothing visibility culling. Godot documents this limitation. Splitting instances spatially should be considered only when profiling demonstrates it matters.

The project remains on `gl_compatibility`. That is a compatibility policy, not evidence of high-end rendering quality. Changing to Forward+ without a defined target hardware/render-feature requirement would be speculation, so this audit does not change it.

### Localization — fixed foundation

The project now registers gettext `.po` catalogs for English and Russian and routes HUD strings through `tr()`. CI starts the actual scene with `--language ru` so catalog/resource loading is exercised.

This establishes localization architecture. Font coverage/fallback, RTL layouts, pluralization beyond current strings, pseudolocalization, and translation workflow automation are not yet verified.

### Design system — fixed foundation

A shared Godot `Theme` resource now owns the base HUD typography/colors/panel style and is applied at the HUD root. Layout-only margin/separation overrides remain local, which is consistent with Godot's theme guidance.

This is a design-system foundation, not a finished visual language. Production UI still needs component variants, focus states, accessibility targets, spacing/type tokens if the UI expands, and actual UX validation.

## Validation gates added

The Godot CI already compiled the GDExtension and ran a native API smoke script. This pass adds a mandatory headless launch of the actual `main.tscn` in Russian locale for two iterations. That catches parse/load failures in the GDScript viewer, scene, Theme, InputMap-backed project startup, and gettext resources that the native API smoke alone could miss.
